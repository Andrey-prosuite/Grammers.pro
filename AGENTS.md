# Правила работы над Grammers.pro

## Ведение этого файла

- Поддерживать `AGENTS.md` в актуальном состоянии при изменении согласованных требований, стека, структуры или команд проекта.
- Фиксировать устойчивые решения и ограничения; не превращать файл в журнал действий и временных ошибок.
- Новые указания пользователя имеют приоритет. При изменении правил согласованно обновлять `README.md` и `docs/architecture.md`, если они затронуты.
- Общаться с пользователем по-русски. Не предполагать, что пользователь умеет запускать локальный сервер.

## Цель и стек

Разрабатываем статическую вёрстку сайта с последующим переносом в WordPress. Страницы состоят из повторно используемых блоков с разным контентом и небольшими вариациями оформления.

- Vite для разработки и сборки, Nunjucks для шаблонов.
- Исходные стили — SCSS с вложенностью; результат сборки — обычный CSS.
- Обычный JavaScript в ES-модулях и jQuery. Не вводить React, Vue или другой клиентский фреймворк без запроса пользователя.
- Node.js >= 22.12.0, зависимости устанавливать через `npm ci`; сохранять `package-lock.json` при изменении зависимостей.
- Для анимаций использовать GSAP: появления и сценарии по скроллу через ScrollTrigger. Предусмотреть плавный скролл; выбор его реализации пока не согласован. Библиотеки ещё не установлены.
- Общую инфраструктуру скролла держать отдельно от анимаций блоков; учитывать `prefers-reduced-motion`, очистку анимаций и работу якорей. Не скрывать контент навсегда при ошибке JS.

- Оригинал: `https://grammers.pro/home-page` (существующая страница на Тильде).

- Сейчас реализовать только HTML (через существующие шаблоны) и SCSS, без пользовательского JS, анимаций и эффектов. Ранее запланированные GSAP и плавный скролл относятся к последующим этапам.
- Минимизировать DOM: семантические элементы, только необходимые обёртки, без служебной разметки и стилей Тильды. Сохранять доступность, адаптивность и SEO-смысл заголовков.

## Структура и блоки

- `src/blocks/<name>/`: шаблон `<name>.njk`, стили `<name>.scss`, поведение `<name>.js` только при необходимости. На текущем этапе стили подключаются через `@use` из `src/styles/main.scss`, без JS-точек входа. Для будущего поведения допустим `index.js`.
- `src/components/`: небольшие переиспользуемые элементы.
- `src/pages/`: порядок и композиция блоков; `src/layouts/`: общий каркас; `src/data/`: контент отдельно от разметки.
- `src/styles/`: общие токены, базовые стили и контейнеры. Стили секций хранятся в самих блоках.
- Базовый класс `.block-name` содержит общие правила. Дополнительный `.block-name-individualclass` задаёт отличия на том же элементе: `class="hero hero-home"`.
- Внутренние элементы именовать `.block-name__element`; использовать SCSS-вложенность `&__element`, `&:hover`, `&.block-name-variant`, избегать глубокой вложенности.
- Не связывать блок с порядком соседей, глобальными тегами или классом страницы. Общие зависимости должны быть явными.
- Повторяемые шаблоны получают явные данные. Для нескольких экземпляров блока обеспечивать уникальные ID и корректные ARIA-связи.
- JS ограничивать экземпляром блока, делать инициализацию повторно безопасной. Для поведения использовать `data-*`; jQuery импортировать через `import $ from 'jquery'`.
- Сохранять семантику HTML, управление с клавиатуры, видимый фокус и доступность контента без JS. Проверять адаптивность.

## Подготовка к WordPress

- Сохранять независимые шаблоны и стабильные CSS-классы для переноса в `template-parts/blocks/`.
- Не дублировать статические шаблоны предварительными PHP-заглушками. Выбор Gutenberg/ACF пока не сделан.
- При переносе использовать WordPress API для контента, меню, ресурсов и экранирования вывода.
- Подключать стили и скрипты через enqueue API. Использовать jQuery WordPress без второй копии, проверив совместимость API с её версией.
- Подробности архитектуры: `docs/architecture.md`.

## Проверка и Git

- `npm run dev` — сервер разработки; `npm run build` — сборка; `npm run preview` — проверка сборки. Итоговый `dist/index.html` с относительными путями также предназначен для открытия двойным щелчком, без localhost.
- На текущем этапе проверять отсутствие `<script>`, inline-обработчиков и внешних запросов ресурсов в production HTML; форма не отправляется до отдельной реализации backend.
- После изменений шаблонов, стилей или JS выполнять сборку. При изменении поведения проверять его в браузере; при изменении вёрстки — мобильную и широкую ширину.
- Для изменений только документации сборка не требуется; проверить diff и `git diff --check`.
- Не редактировать `dist/` и `node_modules/`, не коммитить их или секреты.
- Сохранять чужие изменения; не применять force push и не переписывать историю без явного запроса.
- Основная ветка — `main`; репозиторий — `Andrey-prosuite/Grammers.pro`. Пользователю важно получать исходники в GitHub. Для согласованных изменений поддерживать репозиторий актуальным, сообщать результат отправки.
- Облачный localhost недоступен на компьютере пользователя. Не выдавать внутренний адрес за публичный предпросмотр и не обещать доступ по неподтверждённой ссылке.
- Пользователь работает в Windows 11 и GitHub Desktop. Для автоматического получения исходников предусмотрен `SYNC-FROM-GITHUB.cmd` → `tools/sync-from-github.ps1`: только fast-forward из `origin/main`, без push/reset/stash, с пропуском локальных правок, неотслеживаемых файлов и локальных коммитов. Не добавлять автоматическую отправку или сброс изменений без отдельного запроса. Скрипт не устанавливает зависимости и не пересобирает `dist/`.
