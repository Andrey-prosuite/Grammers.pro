# Правила разработки и перенос на WordPress

## Блоки

Каждая секция хранит шаблон, стили и поведение в своём каталоге. Базовый класс `.block-name`, вариант — дополнительный `.block-name-individualclass` на том же элементе. Внутренние элементы — `.block-name__element`. Пример: `class="hero hero-home"`.

Базовые правила остаются в `.hero`; `.hero-home` задаёт только отличия, преимущественно через CSS-переменные. Не привязывать блок к странице через `body`, порядку соседей, ID или глобальным тегам. Блок может использовать общие токены, контейнер и явно подключаемые компоненты. Не использовать каскадные слои: при отдельном подключении файлов в WordPress порядок должен оставаться предсказуемым.

Шаблоны повторяемых секций оформлять макросами с явным объектом данных. Страница выбирает порядок, контент и вариант. Для повторения секции использовать уникальный идентификатор экземпляра, если нужны `id` и ARIA-связи; пример hero предназначен для единственного H1 на странице. Значения вариантов и URL должны приходить из доверенных данных; при переносе проверять их на сервере.

JS блока экспортирует `initBlock(root = document)`. Поиск элементов и обработчики ограничивать корнем экземпляра; инициализация должна быть повторно безопасной. Для поведения использовать `data-*`, не глобальные переменные и inline-обработчики. JS добавлять только при необходимости. Без JS базовый контент остаётся доступным. Для будущего редактора с удалением экземпляров предусматривать снятие обработчиков/наблюдателей.

Новый блок подключается через свой `index.js` в точке входа нужной страницы. Сейчас одна страница и один bundle. При добавлении страниц регистрировать HTML-точки входа в Vite и отдельные данные в конфигурации рендера; не копировать общий каркас.

## WordPress

1. Общий каркас разделить на `header.php`, `footer.php` и шаблоны страниц.
2. Шаблоны блоков переносить в `template-parts/blocks/<name>.php`, передавать данные через аргументы `get_template_part`. Имена CSS-классов и DOM-контракт сохранять.
3. Источник контента заменить с `src/data/` на поля WordPress. Повторяемые блоки могут стать Gutenberg-блоками с серверным рендерингом и `block.json`; выбор Gutenberg/ACF делается отдельно, когда будут известны требования редактора.
4. При выводе использовать `esc_html`, `esc_attr`, `esc_url`; HTML-контент разрешать только через подходящий `wp_kses`. Автоэкранирование Nunjucks не заменяет экранирование PHP.
5. CSS/JS подключать через WordPress enqueue API, не вставлять вручную теги из статической сборки. Для темы настроить Vite manifest и входы блоков, чтобы подключать только нужные ресурсы и объявлять зависимости от общих стилей.
6. Навигацию, ссылки на ресурсы, заголовок документа и служебные хуки заменить WordPress API, включая `wp_head`, `wp_footer`, `body_class` и `language_attributes`.

Папку темы с заглушками PHP сейчас не создаём: источник правды для вёрстки — `src/`. Перенос будет отдельным этапом, без параллельных копий шаблонов.

## SCSS и jQuery

Все исходные стили — `.scss`: Vite компилирует их в обычный CSS. Использовать вложенность `&__element`, `&:hover` и `&.block-name-variant`; избегать глубокой вложенности. Вариант всегда добавляется вместе с базовым классом. Общие Sass-модули при необходимости подключать через `@use`.

JavaScript остаётся обычным ES-модулями без клиентского фреймворка. jQuery установлен через npm; блоки подключают `import $ from 'jquery'`. Глобальные `$`/`jQuery` не требуются. При переносе на WordPress использовать зарегистрированную WordPress зависимость `jquery`, исключив повторную поставку библиотеки сборщиком; в текущей статической сборке jQuery включается локально, без CDN.
